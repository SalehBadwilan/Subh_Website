# خطة بناء CRUD REST APIs لمنصة "صبح"

## القرارات المعتمدة (من إجاباتك)
- **نطاق التغطية**: كاملة ذكية — CRUD للجداول المرجعية/الكيانية، R+C فقط للمالية، R فقط للسجلات append-only.
- **حقن الـ models**: Factory functions — `createProductRoutes({ models })`.
- **Validation**: express-validator.

---

## المرحلة 1: البنية التحتية المشتركة

### 1.1 تثبيت dependencies
```
npm install express-validator
```

### 1.2 ملفات مساعدة جديدة (`src/utils/` و `src/middleware/`)
- **`src/utils/asyncHandler.js`** — wrapper يلتقط async errors ويمررها لـ `next(err)` (مهم لأن Express 5 لا يلتقطها تلقائيًا).
- **`src/utils/ApiError.js`** — كلاس بسيط: `new ApiError(404, 'Not Found')` يحمل `status` فيلتقطه الـ error handler المركزي.
- **`src/utils/paginate.js`** — helper يقرأ `?page=1&limit=20` ويُرجع `{ limit, offset, page }` + يبني استجابة موحّدة `{ ok, data, pagination: {page, limit, total, totalPages} }`.
- **`src/middleware/validate.js`** — middleware يلتقط نتائج express-validator ويعيد `422 { ok:false, errors:[...] }`.

### 1.3 تعديل `src/app.js`
- `bootApp()` يضع `app.locals.models = models` (للحالات الاضطرارية فقط).
- تحسين الـ error handler لتمييز أنواع أخطاء Sequelize:
  - `SequelizeUniqueConstraintError` → 409
  - `SequelizeValidationError` → 422
  - `SequelizeForeignKeyConstraintError` → 400
  - أنواع أخرى → 500/err.status

## المرحلة 2: نمط موحّد لكل وحدة CRUD

لكل جدول سأنشئ ملف routes واحد بطريقة factory. مثال `createProductRoutes({ models })`:

```
POST   /api/products          → create  (validation + 201)
GET    /api/products          → list    (pagination + filtering)
GET    /api/products/:id      → getOne  (404 if missing)
PUT    /api/products/:id      → update  (validation + 404)
DELETE /api/products/:id      → remove  (soft delete للمشروع paranoid، 404)
```

كل handler يستخدم `asyncHandler` + `next(err)`، ويتبع response envelope `{ ok:true, ...payload }`.

## المرحلة 4: ربط الـ routes في `app.js`
في `bootApp()` بعد `bootDatabase()`:
```js
const { models } = await bootDatabase();
const api = Router();
api.use('/categories', createCategoryRoutes({ models }));
api.use('/products', createProductRoutes({ models }));
// ... كل الوحدات
app.use('/api', api);
```

## المرحلة 5: الاختبار الفعلي (مع Supabase)
1. **seed** للجداول المرجعية (إن لزم) أو استخدام الـ seeders الموجودة.
2. **سكربت اختبار آلي** `scripts/test-api.mjs` ينفّذ curl-equivalent لكل endpoint:
   - POST صنف جديد → تحقّق 201 + وجود في DB
   - GET list → تحقّق pagination
   - GET one → 200
   - PUT → تحقّق تحديث الحقل
   - DELETE → تحقّق soft delete
   - سيناريوهات الخطأ: 404 (id غير موجود)، 422 (validation)، 409 (unique)
3. **إصلاح** أي endpoint يفشل (أخطاء FK، أسماء حقول، قيود CHECK).
4. تشغيل السيرفر + اختبار `/api/health` للتأكد من الإقلاع.

## افتراضات سألتزم بها (MVP، موثّقة في README)
1. لا JWT/Auth — الـ endpoints مفتوحة للتطوير (Auth مرحلة لاحقة).
2. كل الـ DELETE هي soft-delete للجداول paranoid، hard-delete لغيرها.
3. الـ transactions المالية لا تُحذف أبدًا ( consistency).
4. Pagination افتراضية: `?page=1&limit=20` (max 100).
